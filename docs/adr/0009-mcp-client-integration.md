# 通过官方客户端接入 MCP

采用 [官方 TypeScript MCP 客户端 SDK](https://github.com/modelcontextprotocol/typescript-sdk)（`@modelcontextprotocol/client`），复用协议与连接实现，避免自写 MCP 协议或为此引入完整 Agent 框架。保留 Weft 自己的模型 HTTP、Agent 生命周期与实际工具记录，模型选择调用，本地适配并执行。

当前已实现命令型 stdio 与 URL 型 Streamable HTTP。第一版规格包含两者；HTTP 认证支持固定 token／API key 或无需认证，凭据沿用统一 Settings 保存方式，浏览器 OAuth 登录延期。stdio 由 Weft 启动进程，HTTP 连接用户指定的服务 URL，本机 HTTP 服务也属于 URL 型。

第一版至少支持用户当前 Codex 的 Jira MCP 功能：通过 stdio 启动 Docker 中的 `ghcr.io/sooperset/mcp-atlassian`，支持启用开关、完整参数及 120 秒启动超时。复用该 MCP 服务实际暴露的全部 Jira 工具，不把兼容范围限于搜索或读取，也不在 Weft 中重写 Jira API。这条接入路径无需 OAuth 或 `mcp-remote`；现有 Codex 配置是功能对照，不要求用户沿用独立令牌文件。

MCP 服务沿用现有 Settings modal 配置，在 MCP 页以简表管理：一行一个服务，保留名称、启用、配置片段与环境变量。Settings 只展示配置的保存及校验反馈。第一版用 JSON 片段表达命令、参数、超时等连接配置，使用普通多行输入框及字段校验；环境变量单独以名称／值编辑，不在片段中重复保存 `env`。编辑中的无效内容保留为草稿并在该行提示，沿用 Settings 的保存与错误处理。选择 JSON 可直接使用平台解析能力，减少固定表单字段及额外格式解析依赖。

第一版只提供 Jira 预置配置模板，填入服务行后仍可编辑；模板更新不覆盖已有服务配置。其他服务由用户填写 JSON，不提供通用 stdio 或 HTTP 模板。

JSON 中采用 `<变量名>` 引用同一服务 env 列的值，例如 HTTP `http_headers.Authorization` 可填写 `Bearer <MCP_AUTH>`，不另设 `env_http_headers`。先解析 JSON，再对所有字符串值（含数组和嵌套对象中的值）做一次字面替换，不替换对象键，也不再次展开替换结果；只查找当前服务的 env，不回退到系统环境或其他服务。缺少引用的变量时，明确报告该服务配置错误且不启动连接，其他服务和 Agent 仍可继续。这是 Weft 的变量引用约定，不是 MCP 协议格式；原配置保留占位符，实际值仅在执行时注入，无需模板库。

服务定义持久保存于现有 SQLite 数据库，作为唯一配置来源。与全局 Models 配置同层，供各 Project 使用；配置片段是界面编辑方式，不另设 `~/.weft/mcp.json` 或 TOML 配置文件。

Weft 管理的 MCP 环境变量与 OpenRouter API key 统一采用 Settings 输入及现有 SQLite 保存，沿用自动保存习惯。已有 MCP 服务进入 MCP 页时值默认遮蔽，每个服务可独立显示／隐藏所有环境变量值（包括凭据），禁用服务也可查看。新建 Jira 模板与自定义服务默认启用且值可见；不改变已有服务保存的启用状态，用户可手动禁用。显示状态按服务身份暂存，不写入配置，自动保存不改变它；离开 MCP 页或实际关闭 Settings 后全部重新遮蔽，不清除无效或保存失败的草稿。显示会暴露凭据（包括共享屏幕时），遮蔽只是显示便利，不是加密或访问控制。OpenRouter API key 仍用密码框编辑，连接 JSON 行为不变。第一版维持当前明文保存方式；如以后改用系统钥匙串，应统一调整两者。环境变量是外部程序接收配置的接口，区别于凭据的存储方式：本地按服务配置传入，Docker 通过 `-e 变量名` 转交容器，不要求用户另外维护令牌文件。

用户在 Settings 配置并启用的 MCP 服务视为可信外部集成，按自身启动配置、账号、token 及运行环境权限工作；Jev 审核不隔离这些服务的内部行为。本地负责服务启用检查、参数校验、执行、取消及真实记录。

所有 stdio 与 Streamable HTTP MCP Tool Call 均遵循全局 [Jev 安全审核开关](0004-command-tool-isolation-boundary.md)，默认开启。基础参数及服务启用校验后、调用前，使用真实服务名称、工具名称与说明及完整参数审核，只有有效 allow 才调用同一操作。block 或审核故障返回普通工具错误，不弹人工审批，也不自动重放。开关在下一 Tool Call 生效；取消后迟到的允许结果不能启动原操作。连接建立、发现与清理不是 Tool Call，不经此审核。

Jev 仅判断提交操作的危险性，不评价业务任务是否合理，也不隔离服务内部操作；服务账号、配置及运行环境仍决定实际能力。审核使用现有模型 HTTP 与 Model Call 记录及调用上限，固定最新别名，不附带聊天历史或其他任务背景。

每个 Agent 独立建立并拥有 MCP 客户端连接，同一 Agent 的多轮模型调用复用连接，结束或取消时清理。Root Agent 与 Sub-agent 采用同样的归属规则，不共享 stdio 服务进程；一次新用户提交也会新建连接，可能增加 Docker 启动开销。连接是运行时资源，不在 Agent 上额外持久保存一份配置副本；连接状态与连接错误属于对应 Agent，在 Agent 详情展示，工具调用仍归属实际 Tool Call。全局服务配置没有可代表全部 Agent 的“已连接”状态。独立连接不隔离服务账号下的共享外部数据。

修改配置或启用新服务不会自动替换运行中的 MCP 客户端；同一 Agent 可通过 `mcp_startup` 按稳定 service_id 显式采用最新保存配置，否则下一个 Agent 按正常初始化流程采用。运行中的客户端在显式替换前继续使用原配置。禁用或删除服务立即阻止后续工具调用，已发出的调用允许返回；调用执行前由本地检查当前启用状态，拒绝时向模型返回明确错误。保存不建立连接、发现工具、重启现有连接或自动重放调用。有效且已保存的启用服务在下一个 Agent 按正常流程尝试连接；启用不代表已连接，Jira 空凭据仍由正常连接错误和诊断报告。

错误处理沿用 [ADR 0005](0005-local-execution-and-model-decisions.md)：连接、发现或调用失败均如实展示并告知模型，不视作未配置，也不因单个 MCP 失败自动终止整个 Agent。不自动重放失败或结果不确定的工具调用，后续行动由模型决定。

第一版支持 Tools 的发现、调用及实际文本、图片、结构化结果与错误记录。Resources 浏览和读取、Prompts 模板入口及服务端请求模型调用等能力延期；工具返回的资源链接保留为链接，不冒充已读取内容，未支持内容明确说明。

每次模型请求全量提供内置工具及已启用、已发现的 MCP 工具名称、描述和参数 schema，第一版不引入按需工具搜索或本地语义筛选。MCP 服务数量与模型可调用工具数量不同，一个服务可以提供多个工具；Skill 按 [ADR 0007](0007-skill-discovery-and-invocation.md) 作为工作指导加载，不为每个 Skill 注册 function tool。工具定义本身占用输入上下文，实际开销实施时测量。

后续若实测工具定义的上下文或输入成本明显，再优先评估 OpenRouter Tool Search 等现成的按需发现能力，不自写检索框架；这不改变第一版全量提供的范围。

stdio 与 HTTP 已使用固定的 `@modelcontextprotocol/client@2.3.1` 实现，复用官方连接、发现、调用、取消及关闭。为避免 SDK 的现代 header 校正路径重放调用，每次传入当时发现的 toolDefinition；不自动协商／重试现代协议。实际结果按原顺序转成模型原生内容数组：文本和未支持内容保留原块 JSON，图片走原生 input_image，单独保留图片 metadata 及结果 structuredContent、isError、_meta。资源链接注明尚未读取。

2026-10-14 使用现有 Colima/Docker Jira PAT stdio 配置实测：初始化与分页发现成功，共 49 个 Jira 工具（含写操作），完整工具定义 65,649 UTF-8 字节，inputSchema 共 26,132 字节。只读 jira_search 成功返回一项；未执行真实写操作。日常受控 stdio 服务覆盖写参数透传、连接生命周期、多模态与错误。受控本机 Streamable HTTP 服务已覆盖同一 Settings 保存、实际模型工具目录、固定 token／API key／无认证、调用结果与错误、取消及连接清理；未实测外部 HTTP 服务或付费模型。

URL 行使用 `url`、可选 `http_headers` 与 `startup_timeout_sec`，命令行使用 `command`、可选 `args` 与同一超时字段；不混用两种传输字段。HTTP 复用官方 `StreamableHTTPClientTransport`，不设置 OAuth provider，不回退旧 SSE transport。结束时尝试官方会话删除（服务器可拒绝），最多等待一秒再关闭本地流，避免远程服务阻塞 Agent 清理。

## 2026-10-29 恢复能力设计（已确认范围，尚未实施）

实施规格与验收边界见 [#213](https://github.com/tylerlong/weft/issues/213)。本节记录修订后的设计，前文第一版行为与历史验收不表示同一 Agent 内恢复能力已交付。

目标是让 Agent 在同一次执行中诊断 MCP 连接失败、修复普通前置条件、显式重连并继续原任务。采用通用 MCP 诊断与重连能力，以 Jira 作为验收场景，并在需要时提供 Jira／Docker 使用指导。需要用户操作或无法继续时，由模型决定是否交接及如何提问，本地不增加强制交接流程或审批界面。

Agent 可执行只读诊断和启动已配置但停止的前置服务；重启运行中的基础设施、安装软件或修改系统配置前须征得用户确认。MCP 启用、配置编辑与凭据输入仍由用户在 Settings 完成；Agent 使用安全诊断与已启用服务的重连能力，不通过读取 Weft 数据库或导出凭据来排障。

凭据由本地 MCP 执行路径使用，不作为普通工具定义或诊断内容提供给任务模型。此次不新增出站模型请求或模型输出的脱敏层，保留现有记录脱敏；设计讨论采用用户对所选模型实行 ZDR 的假设，不表示 Weft 已验证服务方保留策略。Agent 与 Jev 的运行数据库访问约束见 ADR 0004 的恢复能力设计补充。

本地提供供 Agent 调用的原子操作；原子操作可包含传统的前置检查与已知故障处理，不等于无恢复能力的底层调用。根据实际启动配置识别受支持的 Jira Docker 集成，并直接检查相关 Docker endpoint；可明确识别为已有且停止的 Colima profile 时，在有界启动后验证 Docker 就绪，不自动创建 profile、切换 Docker context、改写配置、安装软件或重启运行中的 VM。Colima 显示运行但 Docker 不可达不等于 profile 已停止。超出已覆盖情况时返回真实错误，由模型决定后续行动，不编排 Jira 业务任务。显式连接或重连使用最新已保存配置；已有连接在显式重连前保留原配置，已禁用或删除的服务不得连接。这修订上文新增启用及配置修改仅对下一个 Agent 生效的限制。

上述本地确定性处理与模型判断的边界遵循 CONTEXT.md 的全项目规则，不是 Jira 特例。

显式重连决策由 Agent 作出；本地可在一次连接操作中执行已覆盖的前置条件处理，不设置无限重试，也不重放此前失败或结果不确定的业务操作。连接恢复与工具目录刷新后，下一次业务调用仍由 Agent 显式选择。重连只替换该 Agent 对选定服务的连接，移除旧工具后建立新连接；失败时保持该服务未连接并返回错误，不保留旧工具或静默退回旧凭据，不影响其他服务与 Agent。

Jev 范围统一遵循 ADR 0004：开启时所有 Tool Call 在执行前审核，不按工具名称或参数在本地筛选。Agent 显式调用 MCP 启动或重连工具时，对整个实际操作及其已知前置条件处理审核一次，提供必要执行信息及凭据引用，不提供凭据值，不为内部确定性步骤逐项追加审核。应用自动启动 MCP 进程及初始化协议等运行时工作不是 Tool Call。

实施验收须至少执行一次真实 OpenRouter 模型参与的验证，检查模型能否使用诊断与连接工具完成只读 Jira 任务；明确区分受控故障与真实服务验证范围。真实模型验证作为单独、显式运行的验收步骤，不加入默认单元测试、常规测试或 CI，不因运行测试自动消耗 token／费用。确定性故障回归继续使用隔离的受控服务与模拟模型响应。




## 已实施的安全诊断（#214）

`mcp_diagnostics` 已通过现有 Tool Call 路径提供当前保存的服务状态，以及调用 Agent 自己的运行状态／错误／stderr。它区分禁用、失败、可用、已配置但本 Agent 尚未启动的服务；按稳定 `service_id` 查询不存在的服务时返回未配置事实。诊断不导出 Settings，不提供凭据值或 HTTP header 值；stdio 仅提供命令、参数数量与变量引用名，HTTP endpoint 省略 query／fragment。环境变量仅提供名称与值是否已配置。配置与凭据仍由用户在 Settings 管理，诊断不建立客户端。

实际 Tool Call 受同一 Jev 开关、预算、取消和记录约束。任务指令引导模型使用此入口，并禁止直接访问应用运行数据库；细节与尽力而为边界见 ADR 0004。受控 stdio／HTTP 配置与模型请求回归验证诊断、凭据省略及 Jev 门控，未据此声称真实 Jira 或付费模型验收已通过。启动／重连和前置条件处理不由 #214 单独交付。


## #215 已实现的 MCP 客户端生命周期

`mcp_startup({service_id})` 在当前 Agent 内使用最新保存的启用服务配置，关闭该 Agent 的旧客户端并先移除旧工具和处理器；新工具只有在所有分页发现成功后一次发布。下一次模型请求得到新目录，旧工具身份不复用，不会静默路由到其他操作。失败保留真实错误与 stderr，该服务不可用，不退回旧凭据或部分目录，也不重放此前业务调用；其他服务与 Root／Sub-agent 的独立客户端不受替换影响。

自动初始化与显式启动复用同一服务启动路径；服务 startup_timeout_sec 对初始化及全部发现共用一个总时限，Agent 取消会关闭所属客户端及 stdio 进程，HTTP 会话删除最多等待一秒再关闭本地流。取消不表示回滚已发生的外部效果。Settings 保存本身不启动协议或业务调用，禁用／删除仍在执行前（含 Jev 审核后）检查。显式启动作为一个 Tool Call 遵循全局 Jev 开关，Jev 接收未展开的实际启动参数及凭据引用；审核期间该服务配置改变时拒绝本次启动并保留旧客户端，模型可再次请求以审核最新配置，其他服务的编辑不影响本次操作。内部协议步骤不再次审核，自动 Agent-start 设置不是 Tool Call。

隔离的 stdio／HTTP 服务与模拟模型测试已覆盖失败后恢复、配置与凭据替换、分页失败不发布部分工具、旧身份失效、取消和启动时限。Docker／Colima 前置准备由 #216 交付；真实模型及 Jira 验收由 #217 单独执行，本节不证明这些部分已完成。
